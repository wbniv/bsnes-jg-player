Responsive SNES display and side panels

Keep every SNES pixel visible in the traditional 4:3 CRT presentation, make the image as large as the viewport allows, and place only the required metadata and performance panels around it.

Status: implementation and viewport review in progress. Android WASM and Native share the responsive layout calculation; browser WASM keeps its own browser controls with the same 4:3 game geometry.

Raw samples and original TV presentation

The common SNES framebuffer has 256×224 samples, so the raw grid is 256 / 224 = 8 / 7. An actual Super Nintendo was normally viewed on a 4:3 CRT television. Its non-square pixel display made the full game picture appear 4:3. Nintendo describes its modern SNES 4:3 mode as the original look with slight horizontal expansion, separately from square-pixel mode. The responsive game rectangle therefore uses 4:3 while showing the complete source image; device dimensions determine only its size and gutters.

No crop or panel overlap. Scale the complete framebuffer with the horizontal aspect correction needed for the traditional 4:3 presentation.

Geometry formulas

Maximum 4:3 image

A = 4 / 3 Wmax = min(W, A × H) Hmax = Wmax / A Gtotal = W − Wmax

W and H are the safe app viewport, after status/navigation/cutout insets.

Two side rails

GL = GR = (W − Wmax) / 2 split = (GL ≥ Mmin + gap) AND (GR ≥ Pmin + gap)

At 1920×1080: image 1440×1080; left/right gutters 240 each.

One combined landscape rail

S = max(Mmin, Pmin) + 2 × gap Wgame = min(Wmax, W − S) Hgame = Wgame / A

At 1200×900 with S=240: Wgame=960 and Hgame=720. Metadata and performance stack in the same rail.

Portrait rails

Harea = H − Hmeta − Hperf − 2 × gap Wgame = min(W, A × Harea) Hgame = Wgame / A

At 1080×2400 with 220 px metadata, 340 px performance, 24 px gaps: image 1080×810, full-width and 4:3.

Mode-selection flow

1 · MeasureRead safe app viewport W×H and insets from the current device window.
2 · Portrait?Place metadata above and metrics below; maximize the 4:3 image between them.
3 · Landscape guttersIf each side can fit its minimum panel width, use metadata left and performance right.
4 · One rail fallbackOtherwise stack both panels on the side with more room. Reduce the image only enough to reserve that rail.

A normal 16:9 screen prefers black gutters on both sides. Choose the one-rail layout from available gutter widths and panel minima, never from a device model name.

Implementation plan

  1. Define one geometry contract returning layout mode plus rectangles for the game, metadata, and performance panels.
  2. Measure the Android safe content window in physical pixels; expose the same normalized geometry to the WebView so Native GL and WebView panels align.
  3. Use the same formulas in the WASM canvas layout. Recompute after orientation, window-size, or inset changes.
  4. Remove the landscape-only activity lock for phone/tablet use while leaving TV devices in their natural landscape orientation.
  5. Validate exact bounds at 1920×1080, 1200×900, 1080×2400, and a portrait tablet size; compare WASM and Native geometry within one physical pixel.
  6. Capture Cast1 and phone/tablet hardware views; verify panel legibility, 4:3 output from the 256×224 framebuffer, D-pad/touch controls, pause menu, and overlay toggle.

Acceptance criteria

  • The full game image remains 4:3 with all framebuffer samples visible and no cropping or panel overlap.
  • The image is the largest possible under the readable panel minimums.
  • 16:9 uses both side gutters; aspect ratios without enough room for two rails use one combined rail.
  • Portrait phones/tablets use top/bottom rails and reflow on rotation without app restart.
  • All bounds are based on actual safe viewport measurements, not fixed device pixel sizes or model names.
